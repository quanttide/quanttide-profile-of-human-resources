# 全栈工程师绩效标准

> 全栈工程师岗位的绩效标准：交付什么算数、按什么证据判定。与绩效记录（report/performance/）配套——记录用本标准判定，标准用记录校准。

## 有效性的唯一来源：业务验证

**代码存在 ≠ 交付有效。** AI 可以生成任意代码，未经人类按业务流程验证的实现，有效性无法认定。一项工作被判定为有效，必须满足以下三条之一：

1. **被真实使用**：功能在真实业务流程中由人或系统实际运行，产生了业务结果（如：dev 部署链路支撑了后续所有发布）；
2. **通过业务验收**：甲方或负责人按业务流程 walkthrough 后确认行为正确，验收记录留存；
3. **被规范收编**：实现被工程规范覆盖并作为基准条款，后续实现以其为参照。

以下情况**不构成**有效：代码合入主干、测试通过、文档齐全、仍在分支上。这些只是交付的必要条件。

## 交付的判定阶梯

| 状态 | 定义 | 判定依据 |
|------|------|----------|
| 有效 | 经过业务验证（上述三条之一） | 使用记录 / 验收记录 / 规范条款 |
| 未验证 | 已交付但无业务验证证据 | 仅有提交、tag、测试 |
| 有效待定 | 有部分证据但不完整 | 如有代码级集成测试但无业务 walkthrough |
| 未完成 | 期初约定未达成 | 期初约定的完成定义未满足 |
| 已重做 | 交付被负责人重做替代 | 重做提交与原交付的时间线 |
| 滞后 | 随功能新增未跟进的配套（测试/文档/规范） | 配套文件最后提交时间 vs 功能交付时间 |

## 岗位职责对应的有效性要求

全栈工程师的工作横跨前后端与部署，各职责的有效性门槛：

- **服务端功能**：以 beta 晋级为分界。alpha 阶段的功能只有进入 beta（候选发布，通过全部 e2e 与业务 walkthrough）才可判定有效；停留在 alpha 的功能一律为「未验证」。
- **基础设施与部署**：以「后续工作是否依赖」判定。部署链路被后续发布实际使用即有效，这是唯一可以即时判定的类别。
- **测试**：e2e 覆盖必须随功能交付同步更新。功能交付后一个发布周期内无对应 e2e，记「滞后」。测试本身有效性以「发现过真实问题」为最高证据。
- **文档与规范**：以「被他人依据执行」判定。写了没人用不算，被引用进规范或被他人按其操作算。

## 期初约定：判定的锚点

每期工作开始前，负责人与全栈工程师约定：交付物清单、每项「完成」的定义、对应的业务验证方式。**期初约定是绩效判定的唯一锚点**——判定只在期初约定与业务验证证据之间进行，不做事后追加。

期初约定缺失的工作项，默认按上表阶梯从严判定（如 alpha 停留即「未验证」），这也是约定本身要前置的原因。

## 与考核体系的关系

- 招聘考核（微型创业课题）筛选的是思考习惯与协作姿态；本标准衡量的是在岗产出的业务有效性，两者衔接：考核通过 → 入职 → 按本标准逐期记录。
- 绩效记录（report/performance/）按本标准逐期判定并留存证据链，作为晋升、调岗与培训决策的依据——判断有据可查，不依赖个别人的印象。
